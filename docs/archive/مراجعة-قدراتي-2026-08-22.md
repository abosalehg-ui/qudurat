# تقرير مِحَك — مراجعة مستودع «قدراتي» (Qudurat)

> **تاريخ المراجعة:** 2026-08-22
> **نوع المشروع المكتشف:** تطبيق ويب (منصة تعليمية PWA) — طُبّق رابرك التطبيقات: هندسة 45% + UX/UI ‏30% + أمن 25%
> **المنهجية:** قراءة كاملة لـ`app.js` و`app-core.js` و`index.html` و`service-worker.js` و`scripts/check-questions.mjs` والاختبارات وعينة من `questions.js` و`styles.css`، مع تشغيل `npm run verify` فعليًا (نجح: 40 اختبارًا + فحص 504 أسئلة).

---

## 1. نظرة عامة سريعة

منصة تدريب على اختبار القدرات (قياس) لطلاب الثانوية: تدريب حسب الفئة، اختبارات مؤقتة، تحدٍّ يومي، تتبّع تقدم مع نقاط وشارات، ولوحة تحكم للمعلم (إضافة/تعديل/استيراد/تصدير أسئلة). البنية: تطبيق صفحة واحدة (SPA) بلا أي اعتماديات وقت تشغيل — HTML/CSS/JS خام + طبقة PWA للعمل دون اتصال، والتخزين كله في المتصفح (`localStorage`/`sessionStorage`).

- **التقنيات:** Vanilla JS (ES2020+)، Web Crypto (PBKDF2)، Service Worker، خطوط محلية (Tajawal/Amiri woff2 مقسّمة عربي/لاتيني)، CI عبر GitHub Actions (Node 20).
- **الحجم:** حوالي 35 ملفًا، ~10,900 سطر، منها ~5,100 سطر بيانات أسئلة (`questions.js`). المنطق الفعلي: `app.js` (2,055) + `app-core.js` (427) + `styles.css` (1,417) + `index.html` (661).
- **ملاحظة سياق:** المستودع مرّ بجولات مراجعة سابقة (`ENGINEERING_REVIEW.md` والـPRs ‏7–9)، وأغلب ملاحظات تلك الجولات مُصلّحة فعلًا في الكود الحالي — هذا التقرير يقيّم الحالة الراهنة.

## 2. المراجعة التقنية والهندسية (45%)

### 2.1 البنية المعمارية وفصل المسؤوليات — 8.5/10

الفصل الثلاثي واضح ومقصود: `app-core.js` دوال نقية بلا DOM (تُصدَّر لـNode فتُختبر مباشرة)، `app.js` طبقة العرض والحالة، `questions.js` بيانات فقط. تصنيف المحتوى (`SUBCATEGORIES`) مصدر واحد للحقيقة يستهلكه التطبيق وفاحص CI معًا — قرار ممتاز يمنع تباعد النسخ.

الملاحظة: `app.js` بـ2,055 سطرًا صار يجمع 12 مسؤولية (توجيه، جلسة، مؤقت، تلعيب، لوحة تحكم، استيراد/تصدير، طباعة…). مقسّم بتعليقات أقسام واضحة، لكنه على أعتاب الحجم الذي يصعب معه التطوير المتوازي. الحل عند أول توسعة قادمة: تقسيمه لملفات حسب القسم (`admin.js`, `session.js`, `gamification.js`) تُحمَّل بنفس ترتيب `<script>` بلا نظام بناء — التقسيم الآن ليس ضروريًا، لكنه يصبح كذلك إن تجاوز الملف ~2,500 سطر.

### 2.2 قابلية القراءة والصيانة — 9/10

تسمية واضحة، دوال قصيرة الغالب، والتعليقات تشرح «ليش» لا «وش» — مثال نموذجي من `app-core.js`:

```js
// الصيغة القديمة كانت تخزّن قاعدة الأسئلة كاملة؛ نستخرج منها محتوى
// المستخدم فقط. لا نستنتج الحذف من الغياب: بيانات إصدار أقدم قد
// تنقصها أسئلة أُضيفت لاحقاً، واعتبارها محذوفة يمنع وصولها نهائياً.
```

هذا مستوى توثيق قرارات نادر في مشاريع بهذا الحجم.

### 2.3 التكرار (DRY) وCode Smells — 8/10

التكرار قليل، لكن فيه ازدواج منطقي حقيقي: حساب «نقاط القوة/الضعف» موجود مرتين بعتبات مختلفة — في `renderResults()` (قوة ≥ 0.7 وضعف < 0.5 بلا حد أدنى للمحاولات) وفي `renderProgress()` (نفس العتبات لكن بشرط `attempted >= 3`):

```js
// renderResults():
const strengths = categories.filter(([, s]) => s.correct / s.total >= 0.7)...
// renderProgress():
.filter(([, s]) => s.attempted >= 3 && s.correct / s.attempted >= 0.7)
```

النتيجة: سؤال واحد صحيح في فئةٍ ما يظهر «نقطة قوة» في شاشة النتيجة، بينما صفحة التقدم لا تعتبره كذلك. الحل: دالة واحدة `classifyCategories(stats, {minAttempts})` في `app-core.js` يستدعيها الموضعان.

### 2.4 معالجة الأخطاء والحالات الحدية — 8.5/10

الجانب الأقوى في المشروع: كل قراءة/كتابة تخزين ملفوفة (`storageGet`/`storageSet`) مع تحذير مستخدم عند امتلاء الحصة، بيانات تالفة تُنسخ احتياطيًا قبل التهيئة (`qudurat_data_corrupt_backup`)، وإضافة سؤال تتراجع (rollback) إذا فشل الحفظ:

```js
userContent.customQuestions.push(newQ);
rebuildDB();
if (!saveData()) {
    userContent.customQuestions.pop();
    rebuildDB();
    return;
}
```

الثغرة المتبقية: **`progress` لا يُتحقق من شكله** لا في `loadData()` ولا في `importAllData()`. الاستيراد يفحص الأسئلة والاختبارات بدقة (`isValidImportedQuestion`) ثم يدمج التقدم كما هو:

```js
if (data.progress && typeof data.progress === 'object' && !Array.isArray(data.progress)) {
    userProgress = pruneProgress({ ...userProgress, ...data.progress });
}
```

لو احتوى ملف النسخة الاحتياطية `"progress": {"savedQuestions": null}` أو `"dailyStats": null`، يمرّ الدمج بنجاح ثم ينهار التطبيق لاحقًا: `userProgress.savedQuestions.includes(...)` في `renderQuestion()` ترمي `TypeError` عند أول سؤال، و`userProgress.dailyStats[today]` في `saveResults()` كذلك (لاحظ أن `typeof null === 'object'` فلا يصدّه فحص `pruneProgress`). الحل: دالة `sanitizeProgress(p)` في `app-core.js` تُجبر كل حقل على نوعه (مصفوفة/كائن/رقم) وتُستدعى في الموضعين — بنفس روح `applyStoredContent` الموجودة أصلًا للمحتوى.

ملاحظة أصغر: `askConfirm`/`askPassword` تحفظ الـresolver في متغير واحد؛ استدعاء متداخل ثانٍ يُسقط وعد الأول بلا حل (promise معلّق للأبد). نادر عمليًا لكن يستحق حارسًا (رفض الفتح إذا فيه طلب معلّق).

### 2.5 الأداء واستهلاك الموارد — 8.5/10

مناسب تمامًا للحجم: جدول الإدارة مُرقّم (50 صفًا/صفحة)، سجل النتائج والإحصاءات اليومية مقصوص (`pruneProgress`)، الخطوط subset ومحمّلة مسبقًا، والأسئلة تُبنى في الذاكرة مرة واحدة. إعادة بناء `innerHTML` للسؤال كاملًا عند كل إجابة مقبولة بهذا الحجم (والكود واعٍ لها: `refreshSavedIndicator` يحدّث زر الحفظ وحده حفاظًا على التركيز). لا توجد مشكلة تُذكر.

### 2.6 الاختبارات — 8/10

موجودة وحقيقية: 40 اختبار وحدة تغطي التهريب والتحقق وCSV ذهابًا وإيابًا والترحيل والقص، **تعمل وتنجح** (`npm test`). يضاف لها فاحص جودة محتوى ذكي (`check-questions.mjs`) يرفض الشروح العامة والخيارات المتساوية قيمةً («1/2» = «2/4») — فكرة فحص نادرة الجودة. CI يشغّل الاثنين على كل push/PR.

الفجوة: صفر اختبارات تكامل في متصفح — التوجيه، الجلسة المستأنفة، المؤقت، ولوحة التحكم كلها غير مغطاة آليًا (وREADME صريح في ذلك). أعلى قيمة بأقل جهد: سيناريو Playwright واحد يمر على: فتح → تدريب → إجابة → نتيجة → استئناف جلسة.

### 2.7 التوثيق — 9.5/10

`README.md` من أفضل ما يُكتب لمشروع بهذا الحجم: بنية التخزين موثقة بجدول، حدود الأمان معلنة بصراحة، جدول «أين أضع الكود الجديد؟»، ومعايير الشرح الإلزامي للأسئلة. الشيء الوحيد الناقص: `ENGINEERING_REVIEW.md` القديم ما زال في الجذر ويصف حالة كود لم تعد موجودة (يتحدث عن ملف واحد بـ11 ألف سطر وSHA-256) — يستحق أرشفة أو حذفًا حتى لا يضلل مساهمًا جديدًا.

### 2.8 اتفاقيات التسمية والنمط الموحد — 9/10

camelCase متسق، أسماء دوال أفعال واضحة، `data-action`/`data-change` نمط موحّد للربط، والثوابت UPPER_CASE. لا ملاحظات جوهرية.

### ⟵ درجة القسم الهندسي: **8.6/10**

## 3. المظهر والتصميم وتجربة المستخدم (30%)

### 3.1 الاتساق البصري — 9.5/10

نظام رموز تصميمية (design tokens) كامل في `:root`: لوحة ألوان موثقة بنسب تباينها، سلّم مسافات (`--space-1..7`)، سلّم أنصاف أقطار، والوضع الليلي يعيد تعريف الرموز نفسها لا القواعد. لا ألوان مبعثرة.

### 3.2 سهولة الاستخدام والتنقل — 9/10

توجيه عبر hash يجعل زر رجوع المتصفح والروابط العميقة تعمل، المهمة الأساسية (بدء تدريب) على بعد نقرتين، واستئناف الجلسة بعد التحديث محمي بحوار. حماية مغادرة الاختبار الجاري (تأكيد + `beforeunload`) مدروسة.

ملاحظة صغيرة: حوار التأكيد يضع التركيز مبدئيًا على زر التنفيذ الخطر (`openModal('confirmModal', '#confirmOkBtn')`) — ضغطة Enter متسرعة تنفّذ الحذف. الأسلم تركيز زر الإلغاء افتراضيًا في الحوارات الهدّامة.

### 3.3 الاستجابة — 9/10

خمس نقاط توقف (1150/900/768/480px) مع تعديلات فعلية لا شكلية (قائمة جوال، جدول داخل `.table-scroll`، أزرار تتمدد `flex: 1 1 100%`). أصغر هدف لمس هو أزرار الثيم 42px عند 480px — فوق الحد الأدنى المريح.

### 3.4 العربية وRTL — 9/10

من الأمتن في هذا الباب: `dir="rtl"` مع **خصائص منطقية** (`inset-inline`, `padding-inline`, `margin-inline` — 20 موضعًا وصفر خصائص فيزيائية يدوية)، خطوط محلية مقسّمة عربي/لاتيني مع `preload`، وأسهم لوحة المفاتيح واعية لانعكاس RTL (تعليق صريح في `handleOptionKeydown`).

الخلل الوحيد — وهو حقيقي ومرئي: تسميات أعمدة رسم آخر 7 أيام في `renderPerformanceChart()`:

```js
<span class="chart-label">${day.name.slice(0, 3)}</span>
```

قصّ أول 3 محارف من أسماء الأيام العربية ينتج: **«الأ | الا | الث | الأ | الخ | الج | الس»** — كلها تبدأ بـ«ال» فتصير بلا معنى، والأدهى أن الأحد والأربعاء يتطابقان («الأ»). الحل: خريطة أسماء قصيرة صريحة `['أحد','اثنين','ثلاثاء','أربعاء','خميس','جمعة','سبت']` بلا قصّ إطلاقًا.

### 3.5 إمكانية الوصول — 9.5/10

فوق مستوى أغلب المنتجات التجارية: skip-link، حصر تركيز في النوافذ مع استرجاعه عند الإغلاق، `role="radiogroup"` مع roving tabindex وأسهم تنقّل، `aria-live` للمؤقت يصير `assertive` في آخر دقيقة فقط (حتى لا يزعج قارئ الشاشة كل ثانية)، نقل التركيز لعنوان الصفحة الجديدة عند التنقل، `prefers-reduced-motion`، ونسب تباين موثقة في CSS. عمل يستحق الإشادة.

### 3.6 التغذية الراجعة — 9/10

Toasts بأنواع، حالة انشغال لأزرار الاستيراد (`is-busy`)، أخطاء نماذج مربوطة بحقولها (`aria-invalid` + `field-error`)، تأكيد قبل كل حذف، ورسائل خطأ بشرية («قد تكون مساحة التخزين ممتلئة… صدّر نسخة احتياطية»). ملاحظة دقيقة: مؤقت الجلسة المستأنَفة يحسب الوقت من `startTime` الأصلي، فجلسة تدريب حرة استؤنفت بعد ساعات تعرض «وقتًا مستغرقًا» متضخمًا في النتيجة — تجميلية لكنها تشوّه الإحصاء.

### ⟵ درجة قسم UX/UI: **9.2/10**

## 4. المراجعة الأمنية (25%)

**تحديد السياق أولًا:** تطبيق أوفلاين بلا خادم ولا API ولا بيانات حساسة، معلَن ذلك صراحة في README. بنود «الصلاحيات الخادمية/CORS/HSTS/قواعد البيانات» **لا تنطبق**، والدرجة محسوبة من المنطبق فقط.

| الملاحظة | الموضع | الخطورة | التقييم |
|---|---|---|---|
| حقن HTML (XSS) | كل القوالب تمرّ عبر `escapeHTML`، والحقول الداخلة في class/سمات محصورة بـ`safeToken`/`safeId`، ومغطاة باختبارات وحدة صريحة لحمولات هجومية | ✅ سليم | ممتاز |
| سياسة أمان المحتوى (CSP) | `index.html`: ‏`script-src 'self'` بلا أي inline handlers (الربط كله عبر تفويض أحداث)، `object-src 'none'`, `base-uri 'none'`, `form-action 'none'` | ✅ سليم | صارم وفعّال |
| كلمة مرور اللوحة | PBKDF2 ‏150k تكرار + ملح عشوائي + مقارنة ثابتة الزمن + تأخير تصاعدي، مع إعلان صريح أنها «تنظيمية لا أمنية» | ✅ سليم | نموذج للتهديد صادق — وهذا أهم من التقنية نفسها |
| حقن صيغ CSV | `escapeCSV` تعطّل `=+-@` وتقتبس عند الحاجة، مع اختبارات round-trip | ✅ سليم | ممتاز |
| التحقق من الاستيراد | الأسئلة والاختبارات تمرّ بفحص نوعي صارم وسقف `MAX_IMPORT_ITEMS = 5000`، **لكن كائن `progress` يُدمج بلا أي فحص شكل** — ملف نسخة احتياطية معطوب يعطّل التطبيق (تفصيل 2.4) | 🟠 متوسط | سلامة تشغيل لا سرية — لكنه أسهل طريق لكسر التطبيق حاليًا |
| `eval` في أداة الفحص | `scripts/check-questions.mjs`: ‏`(0, eval)(source + '\ngetSampleQuestions();')` | 🟡 بسيط | يعمل وقت الـCI فقط على ملف من نفس المستودع؛ مقبول، والأنظف تحويل `questions.js` لوحدة قابلة للـ`require` مثل `app-core.js` |
| تثبيت إجراءات CI | `check-questions.yml`: ‏`actions/checkout@v4` بالوسم لا بالـSHA | 🟡 بسيط | التثبيت بالـSHA يقفل سلسلة التوريد؛ أثره محدود لأن للـworkflow صلاحية `contents: read` فقط — وهذا بحد ذاته ضبط جيد |
| `style-src 'unsafe-inline'` | ضرورة لسمات style في القوالب، موثقة بتعليق | 🟡 بسيط | المخاطرة شبه معدومة مع تهريب كل المدخلات |
| المفاتيح والأسرار | لا مفاتيح، لا `.env`، صفر اعتماديات (سطح سلسلة توريد معدوم تقريبًا) | ✅ سليم | — |

**الخلاصة الأمنية:** المشروع يطبّق دفاعًا بعمق يفوق المطلوب لطبيعته (أداة أوفلاين)، والأهم أنه **صادق في إعلان حدوده**. الثغرة الوحيدة ذات الأثر العملي هي دمج `progress` غير المفحوص.

### ⟵ درجة القسم الأمني: **9.0/10**

## 5. الدرجة الإجمالية المرجّحة

| الناحية | الدرجة | الوزن | المساهمة |
|---|---|---|---|
| تقنية وهندسية | 8.6/10 | 45% | 3.87 |
| UX/UI | 9.2/10 | 30% | 2.76 |
| أمن سيبراني | 9.0/10 | 25% | 2.25 |
| **الإجمالي** | | | **8.9/10** |

الحساب: ‏(8.6 × 0.45) + (9.2 × 0.30) + (9.0 × 0.25) = 3.87 + 2.76 + 2.25 = **8.88 ≈ 8.9**

هذي درجة حقيقية لا مجاملة: المشروع مرّ بجولات إصلاح متتابعة وأثرها ظاهر في كل ملف. ما لا يمكن الحكم عليه من الكود وحده: الجودة التربوية للأسئلة الكمية (المراجعة الرياضية البشرية الشاملة ما زالت بند todo في README)، والسلوك الفعلي على متصفحات غير Chromium.
